## Purpose

Lets the gateway decide, per target model and via configuration, whether an inbound image should be forwarded natively or must first be described as text by a vision-capable model, so that vision-capable target models receive the original image instead of a lossy text substitute.

## ADDED Requirements

### Requirement: Vision capability lookup by target model
The system SHALL determine whether the request's target model has native vision support by looking up the target model's id in a configurable capability registry before deciding how to handle `image_url` content.

#### Scenario: Target model is configured with vision capability
- **WHEN** an inbound chat request targets a model id that the capability registry lists as having vision capability
- **THEN** the system treats that request as targeting a natively vision-capable model

#### Scenario: Target model is configured without vision capability
- **WHEN** an inbound chat request targets a model id that the capability registry lists with no vision capability
- **THEN** the system treats that request as targeting a model that lacks native vision support

#### Scenario: Target model is absent from the capability registry
- **WHEN** an inbound chat request targets a model id that does not appear in the capability registry at all
- **THEN** the system treats that request as targeting a model that lacks native vision support

### Requirement: Image content passthrough for natively vision-capable models
When the target model has native vision support, the system SHALL forward `image_url` content blocks unchanged, without invoking manual vision-description routing.

#### Scenario: Image sent to a natively vision-capable model
- **WHEN** a request targeting a natively vision-capable model contains a user message with an `image_url` content block
- **THEN** the system forwards that content block to the target model without modification and does not generate a text description of the image

### Requirement: Manual vision routing for models without native vision support
When the target model lacks native vision support, the system SHALL replace `image_url` content blocks with a text description produced by a vision-capable model, preserving current behavior.

#### Scenario: Image sent to a model without native vision support
- **WHEN** a request targeting a model without native vision support contains a user message with an `image_url` content block
- **THEN** the system replaces that content block with a text description generated by a vision-capable model before forwarding the request

### Requirement: Capability configuration is externally configurable
The system SHALL allow operators to declare each model's supported capabilities via configuration, without requiring a code change to add or update a model's vision capability.

#### Scenario: Operator adds a new vision-capable model
- **WHEN** an operator adds a model id with vision capability to the configuration and restarts the gateway
- **THEN** subsequent requests targeting that model id are treated as natively vision-capable without any code change

#### Scenario: Operator declares an unrecognized capability value
- **WHEN** the configuration contains a capability value that is not a recognized capability
- **THEN** the system fails to start rather than silently ignoring or misinterpreting the value
